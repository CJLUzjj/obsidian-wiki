# Wiki 查询 — 知识检索

您正在回答针对已编译的黑曜石维基的问题，而不是原始源文档。维基百科包含预先综合的、交叉引用的知识。

## 开始之前

1. 读取`~/.obsidian-wiki/config` 以获取`OBSIDIAN_VAULT_PATH`（适用于任何项目）。如果您位于 obsidian-wiki 存储库中，请返回 `.env`。
2. 如果 `$OBSIDIAN_VAULT_PATH/hot.md` 存在，请先阅读它 — 它为您提供有关最近活动的即时背景信息。如果用户的问题是关于最近摄取的某些内容，hot.md 可能会在您打开`index.md` 之前就回答它。
3. 阅读 `$OBSIDIAN_VAULT_PATH/index.md` 以了解 wiki 的范围和结构

## 可见性过滤器（可选）

默认情况下，**返回所有页面**，无论可见性标签如何。这保留了现有的行为——除非用户要求，否则不会发生任何改变。

如果用户的查询包含诸如**“仅公开”**、**“面向用户”**、**“无内部内容”**、**“用户会看到的”这样的短语，或 **“排除内部”**，则激活 **过滤模式**：

- 构建**被阻止的标签集**：`{visibility/internal, visibility/pii}`
- 在索引通道（步骤 2）中，跳过其 frontmatter 标签包含被阻止标签的任何候选者
- 在部分/完整阅读通行证（步骤 3-4）中，请勿阅读或引用任何被阻止的页面
- 仅从允许的页面合成答案 - 不要提及存在排除的页面

始终包含没有 `visibility/` 标记或标记为 `visibility/public` 的页面。

在过滤模式下，记下步骤 6 日志条目中的过滤器：`mode=filtered`。

## 检索协议

**遵循 `llm-wiki/SKILL.md` 中的检索基元表。** 阅读是此技能的主要成本 - 使用能够回答问题的最便宜的基元，只有在无法回答问题时才升级。切勿直接跳至整页阅读。

### 第 1 步：理解问题

对查询类型进行分类：
- **事实查找** — “X 是什么？” → 查找相关页面
- **关系查询** — “X 与 Y 有何关系？” → 查找两个页面及其交叉引用
- **综合查询** — “目前对 X 的想法是什么？” → 找到所有接触X的页面，合成
- **差距查询** — “关于 X，我不知道什么？” → 查找缺少的内容，检查未解决的问题部分

还决定 **模式**：
- **仅索引模式** — 由“快速回答”、“仅扫描”、“不阅读页面”、“快速查找”触发。停在步骤 3。仅来自 frontmatter + `index.md` 的答案。
- **普通模式** — 下面的完整分层管道。

### 第 2 步：索引通行证（便宜）

构建候选集*无需打开任何页面主体*：

- 您已经阅读了上面的`index.md` - 将其用作第一个过滤器。它列出了每个页面，并带有一行描述和标签。
- 使用`Grep` 扫描页面**仅前文**以查找标题、标签、别名和摘要匹配。像`^(title|tags|aliases|summary):` 这样的模式，作用范围为Vault `.md` 文件，比内容grep 便宜得多。
- 收集排名前 5-10 名的候选页面路径：
  1. 标题或别名完全匹配
  2. 标签匹配
  3. 摘要字段包含查询词
  4.`index.md`条目包含查询词

如果您处于**仅索引模式**，请在此停止。仅来自 `summary:` 字段、标题和 `index.md` 描述的答案。清楚地标记答案：**“（仅索引答案 - 未阅读页面正文；以下事实来自页面摘要，可能会忽略细微差别）”**。然后跳到步骤 5。

### 步骤 2b：QMD 语义通行证（可选 — 需要 `.env` 中的 `QMD_WIKI_COLLECTION`）

**GUARD：如果 `$QMD_WIKI_COLLECTION` 为空或未设置，请跳过整个步骤并继续执行步骤 3。**> **没有 QMD？** 跳到步骤 3 并直接在保管库上使用 `Grep`。 QMD 速度更快且具有概念意识，但 grep 路径功能齐全。请参阅`.env.example`进行设置。

如果设置了`QMD_WIKI_COLLECTION`并且索引传递没有产生明确的候选者 - 或者问题需要语义匹配而不是精确的术语 - 在到达`Grep`之前使用QMD：```
mcp__qmd__query:
  collection: <QMD_WIKI_COLLECTION>   # e.g. "knowledge-base-wiki"
  intent: <the user's question>
  searches:
    - type: lex    # keyword match — good for exact names, file paths, error messages
      query: <key terms>
    - type: vec    # semantic match — good for concepts, patterns, "what is X like"
      query: <question rephrased as a description>
```
返回的片段充当预读部分摘要。如果他们完全回答了问题，请跳过步骤 3，直接进入步骤 4（仅阅读 QMD 排名最高的页面）。如果没有，请使用排名文件列表来指导在步骤 3 中 grep 或读取哪些文件。

**当问题可能在`_raw/`中包含源材料时，还可以搜索`papers`：**

如果设置了 `QMD_PAPERS_COLLECTION` 并且用户正在询问可能包含在摄取论文中的主题（研究、理论、背景），则针对论文集合运行并行搜索。在您的答案中分别引用原始来源和已编译的 wiki 页面。

### 步骤 3：部分通过（中等成本 — 仅当步骤 2/2b 没有结果时）

对于每个排名靠前的候选人，请拉出相关部分*而不阅读整页*：

- 使用`Grep -A 10 -B 2 "<query-term>" <candidate-file>` 只获取比赛周围的线条。
- 每次点击通常会返回 15-30 行，而不是 100-500 行。
- 如果 grep 部分给出了明确的答案，则直接转到步骤 5。

### 步骤 4：完整阅读（昂贵 - 最后的手段）

仅当步骤 2 和 3 不能回答问题时：

- `Read` 前 **3** 候选人全部。
- 如果答案需要交叉引用，则最多从这些页面跟踪 `[[wikilinks]]` 的一跳。
- 检查“开放问题”部分是否存在已知差距。
- 如果您仍然不够，**然后**退回到跨保险库的广泛内容 grep。告诉用户你升级了——这是一条昂贵的途径，他们应该知道。

### 第 5 步：综合答案

根据 wiki 内容撰写您的答案：
- 使用 `[[page-name]]` 符号引用特定的 wiki 页面
- 注意答案来自哪一步（“在摘要中找到”与“grepped 部分”与“整页阅读”）——帮助用户理解信心
- 如果维基有矛盾，请提出双方
- 如果维基百科没有涵盖某些内容，请明确说明
- 建议哪些来源可以填补空白

### 第 6 步：记录查询

附加到`log.md`：```
- [TIMESTAMP] QUERY query="the user's question" result_pages=N mode=normal|index_only|filtered escalated=true|false
```
## 答案格式

结构答案如下：

> **基于维基：**
>
> [您使用 [[wikilinks]] 到源页面的综合答案]
>
> **查阅的页面：** [[page-a]]、[[page-b]]、[[page-c]]
>
> **差距：** [维基百科未涵盖但可能相关的内容]
